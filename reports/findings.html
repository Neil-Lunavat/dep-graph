Which files should you read, and in what order, before changing one file?

We ran 30 ordering methods (plus 4 simple references) on 3,123 tasks (one per starting file) from 1,873 real bug-fix PRs in 113 Python repositories, and measured how much code each method's list made you read before you had seen the files the change needed. No language model is used anywhere.

What was measured

Graph-walking methods cover the key faster than random, by a wide marginBest overall: Personalised PageRank (undirected), area under the curve 0.44 (95% CI 0.41–0.46) vs 0.25 for random order. Vargha–Delaney A12 vs random = 0.75 (0.5 = no difference).
But which method leads depends on the evidence used as the answer keyWith the co-edited-files key (independent of imports), text search (BM25) and co-change history rank near the top. With the symbol key, which overlaps the import graph by construction, graph methods lead.
Needed files sit close to the starting fileMost answer-key files are 1–2 import hops away (ignoring direction). Few have no path at all. Following imports in one direction only misses about a third.
There is a large gap to the ceilingA cheat ceiling that already knows the answer reaches 0.78. The best real method reaches 0.44, so there is room for better orderings.

The answer key changes the ranking

This is the most important caution. The symbol key comes from resolving names in the new code, and a file that defines a name you use is usually one you import. So it favours import-graph methods by construction. The co-edited key has no such link, and on it text similarity and history do as well as or better than graph walks.

RQ2 · Does repository shape predict which method helps?

We correlated every Table 1 property with every method's gain over random, across repositories: 990 pairs, Benjamini–Hochberg corrected. 326 pairs are significant at 0.05. The strongest are mostly about size. In bigger repositories the random floor drops, so every method's gain grows. This is exploratory and size is a likely confounder; we have not separated it out yet.

  • closure_rev × loc_total: ρ = 0.69
  • closure_rev × largest_loop: ρ = 0.64
  • bfs_rev × loc_total: ρ = 0.64
  • bfs_rev × largest_loop: ρ = 0.63
  • closure_fwd_trim × import_edges: ρ = 0.63

Which method was best per repository varies: Personalised PageRank (imports) (20), Personalised PageRank (undirected) (15), PageRank (global) (12), Robillard specificity×reinforcement (10), Aider repo-map (adapted) (8).

Do the three kinds of evidence agree?

On the 100 tasks with an execution run so far: the static key (co-edited + symbol) has 3.2 files on average, and the execution key (lines inside functions that ran during the fixing tests) has 20.0. 55% of static-key files also ran; only 9% of executed files are in the static key. Mean overlap (Jaccard) = 0.18. So running the tests touches far more code than the static evidence points to. That's a result about the limits of static analysis, not a bug.

How to read these numbers

  • The answer key is a floor. It contains files with evidence attached and misses files a developer only read. Methods are never penalised for listing extra files, only charged for the reading.
  • Published approaches (Aider, RepoGraph, LocAgent, CoSIL) appear as structure-only adaptations, with no issue text and no model. These numbers must never be compared with the published ones.
  • Unit of analysis: the PR (a PR's tasks are averaged). Ties inside any method are broken randomly, averaged over 5 seeds.
  • Every rule was written down before any method ran (git tag freeze-1). Every change is logged.
